# Git 운영 · 진행 요약 (오케스트레이터용)

> 기준 문서. 프로젝트 저장소 커밋·태그·진행 요약(`ACTIVITY.md`)·고객 인도 패키지의 상세 규칙. 원칙은 `CLAUDE.md` §9.

## 1. 커밋 시점과 메시지 — 작업 단위마다
산출물이 바뀌면 그때그때 커밋한다. 한 작업 단위 = **에이전트 1회 호출**(병렬 호출이면 그 배치 전체)이며, 배치가 끝난 뒤 한 번 커밋한다. 커밋하지 않은 채 다음 에이전트를 호출하지 않는다.

| 작업 단위 | 커밋 메시지 | 태그 |
|---|---|---|
| kickoff 골격 생성 + CR-000 기록 | `chore(kickoff): 프로젝트 생성 및 고객 요청 기록` | `kickoff` |
| 산출물 작성 | `docs({단계}): {문서} v{버전} 작성 — {팀}` | — |
| 리뷰 반영 | `docs({단계}): {문서} v{버전} R{n} 리뷰 반영 — {팀}` | — |
| 교차 검토 (병렬 배치 1커밋) | `review({단계}): {대상} R{n} — {검토자들}` | — |
| 구현 (작업 단위별) | `feat(P4): {작업 단위 요약} — developer` | — |
| 결함 수정 | `fix(P5): DEF-{nnn} {요약} — developer` | — |
| 테스트 실행·결과 | `test(P5): {요약} — qa` | — |
| 게이트 문서 작성 | `docs(G{n}): 게이트 문서 작성 — pmo` | — |
| 게이트 PM 승인 | `gate(G{n}): {단계명} 승인` | `G{n}` (CR 회귀 후 재승인: `G{n}-CR-{nnn}`) |
| CR 접수·분석·PM 결정 | `cr(CR-{nnn}): {요약}` | — |
| 제안 접수·검토·PM 결정·반영 | `sug(SUG-{nnn}): {접수 \| 검토 — {팀들} \| PM 결정 — {결정} \| 반영}` | — |
| 고객 답변 기록·반영 | `qna(Q-{nnn}): {답변 기록 \| 반영 — {문서}}` | — |
| PM 배포 승인 직후 (배포 실행 전) | `release: v{x.y.z} 배포 승인` | `release-v{x.y.z}` |
| 배포 실행 결과 | `chore(P7): 배포 실행 결과 기록 — devops` | — |
| 그 외 (STATUS 갱신, 티켓 처리, 반입 자료 저장, 스크린샷 캡처 등) | `chore: {요약}` 또는 단계 범위를 붙여 `chore(P{n}): {요약}` | — |
| 세션 재개 전 작업분 보존 (PM 동의 시) | `chore: 세션 재개 전 작업분 보존` | — |
| 프로젝트 종료 | `chore(close): 프로젝트 종료` | — |

- 커밋 메시지 본문에는 변경 요약과 관련 문서·리뷰·티켓 경로를 적는다.
- 태그는 annotated tag로 만들고 메시지에 게이트 문서 경로와 승인 일시를 적는다.
- 릴리스 버전: 최초 오픈 `v1.0.0`, 이후 CR 기능 추가 `minor`, 결함 수정만 `patch` 증가.

## 2. 커밋 전 점검
1. `git -C {PROJECT} status --short` — `.env`, 비밀 정보, `node_modules`·`vendor/`·`.venv/`, 대용량 파일, `{PROJECT}` 밖 경로가 없는지 확인한다. 의심 파일이 있으면 커밋하지 말고 PM에게 알린다.
2. 틀 루트에서 `git status --porcelain` — 보호 영역에 의도치 않은 변경이 없는지 확인한다(Bash를 통한 쓰기는 권한 규칙으로 막히지 않기 때문). 있으면 프로젝트 커밋을 멈추고 PM에게 알린다.
3. 에이전트 완료 보고에 `{PROJECT}` 밖 경로가 있으면 커밋하지 말고 PM에게 알린다.
4. `{PROJECT}/ACTIVITY.md`에 이 작업 단위의 항목을 추가했는지 확인한다(§3).

## 3. 진행 요약 `{PROJECT}/ACTIVITY.md`
팀별 `WORKLOG.md`와 별도로, **프로젝트 전체 진행을 한눈에 보는 요약**을 프로젝트 루트에 둔다.

- **WORKLOG와의 관계**: 둘 다 유지한다. `ACTIVITY.md` = 전 팀의 "무엇을 했나"(오케스트레이터, 1~2줄), `{팀}/WORKLOG.md` = 각 팀의 "어떻게·왜 했나"(에이전트).
- **작성 주체**: 오케스트레이터만 (에이전트는 쓰지 않는다 — 병렬 작업 충돌 방지).
- **시점**: 작업 단위 커밋마다 항목을 추가하고 **같은 커밋에 포함**한다. 의미 없는 갱신(STATUS 동기화 등)은 생략할 수 있다.
- **정렬**: 날짜(`### YYYY-MM-DD`, 로컬 날짜)별로 묶고 **최신 날짜가 위**, 같은 날짜 안에서도 **최신 항목이 위**. 오늘 날짜 묶음이 없으면 안내문 바로 아래에 만든다.
- **항목 형식**: `* {구분}: {무엇을 했고 결과가 무엇인지 1~2줄} ({팀})` — ID·버전·핵심 수치를 넣는다(에이전트 완료 보고의 "핵심 내용 요약"에서 뽑는다). 파일 경로는 필요할 때만.
- **구분**: `추가`(새 산출물·기능) · `수정`(개정·리뷰 반영·결함 수정) · `검토`(리뷰 판정) · `검증`(테스트 실행 결과) · `결정`(PM 승인·선택·ADR·CR 결정) · `배포` · `이슈`(블로커·예외 진행·회귀·중단)
- 지난 항목은 고치지 않는다. 정정이 필요하면 새 항목으로 적는다.

```
### 2026-10-02

* 결정: G2 기획 승인, 스택 프리셋 `kr-shared` 확정 (ADR-002) (PM)
* 검토: 요구사항·IA·화면정의서 R1 — 조건부 승인, Must 0 · Should 2 (developer)
* 추가: 요구사항 정의서 v0.1 — REQ 24건(Must 12), 화면 SCR 8개 (planner)
```

## 4. 고객 인도 패키지 (P8, G8 승인 후)
- 인도 범위(예: 소스·운영 가이드·최종 보고서만 / 전체)는 PM이 결정한다. 내부 리뷰·티켓·WORKLOG·ACTIVITY 포함 여부를 반드시 확인받는다.
- 방식: ① `git archive`로 승인된 태그 기준 선택 경로 zip(기본) ② `git bundle`로 전체 이력 ③ PM 승인 후 고객 저장소 push — 결과는 `{PROJECT}/.delivery/`(git 제외). 패키지에는 목차 README와 라이선스·출처 목록을 넣고 `.env`·비밀 정보가 없는지 확인한다.

## 5. 원격 저장소
원격 저장소 생성·연결·push는 **PM이 지시한 경우에만** 수행한다. 커밋은 작업 단위마다 하되, push는 지시 없이 하지 않는다.
